# IAM Configuration for Automated Scheduler Deployment

This document details the permission infrastructure (IAM) necessary for Cloud Build to automatically deploy Google Cloud Scheduler tasks, maintaining a Least Privilege architecture.

## 🏛️ The Identity Architecture (The "What")

To avoid over-privileged permissions, the system divides responsibilities into two actors with separate identities:

1.  **The Execution Identity (Scheduler SA):**
    *   **Name:** `lifeos-scheduler-sa`
    *   **Role:** The "Night Watchman". Its only purpose is to wake up at the scheduled time and make an HTTP request to the *Worker*.
    *   **Required Permission:** `roles/run.invoker` (Exclusively on the Worker service in Cloud Run).

2.  **The Deployment Identity (Cloud Build SA):**
    *   **Name:** `{PROJECT_NUMBER}@cloudbuild.gserviceaccount.com` (Automatically generated by GCP).
    *   **Role:** The "Manager". It is responsible for reading the code and creating the infrastructure.
    *   **Required Permissions:**
        *   `roles/cloudscheduler.admin`: To be able to create and modify *jobs* in Cloud Scheduler.
        *   `roles/iam.serviceAccountUser`: **Critical.** This is the "impersonation" permission. It allows Cloud Build to tell GCP: *"Create this cron and have the Scheduler account run it"*. Without this, GCP blocks the deployment for security.

## 🛠️ Step-by-Step Configuration (The "How")

Run these commands in the terminal authenticated with your administrator user to prepare the ground before the first deployment.

### 0. Environment Variables

```bash
export PROJECT_ID="your-project-id" # The alphanumeric ID
export REGION="europe-west1"      # The region where your Cloud Run lives
export WORKER_SERVICE="lifeos-worker" 
export PROJECT_NUMBER=$(gcloud projects describe $PROJECT_ID --format='value(projectNumber)')
export CLOUDBUILD_SA="${PROJECT_NUMBER}@cloudbuild.gserviceaccount.com"
```

### 1. Enable Required APIs

```bash
gcloud services enable cloudscheduler.googleapis.com --project=$PROJECT_ID
gcloud services enable run.googleapis.com --project=$PROJECT_ID
gcloud services enable cloudbuild.googleapis.com --project=$PROJECT_ID
```

### 2. Configure the Execution Identity (Scheduler SA)

We create the dummy account that will run the crons and give it permission to knock on the Worker's door:

```bash
# Create the account
gcloud iam service-accounts create lifeos-scheduler-sa \
    --description="Cron executor for LifeOS" \
    --display-name="LifeOS Scheduler SA" \
    --project=$PROJECT_ID

# Give it Invoker badge on Cloud Run
gcloud run services add-iam-policy-binding $WORKER_SERVICE \
    --region=$REGION \
    --member="serviceAccount:lifeos-scheduler-sa@${PROJECT_ID}.iam.gserviceaccount.com" \
    --role="roles/run.invoker" \
    --project=$PROJECT_ID
```

### 3. Configure the Deployment Identity (Cloud Build SA)

We give powers to the CI/CD pipeline account so it can create the infrastructure and use the previous account:

```bash
# Permission to manage the Scheduler
gcloud projects add-iam-policy-binding $PROJECT_ID \
    --member="serviceAccount:${CLOUDBUILD_SA}" \
    --role="roles/cloudscheduler.admin" \
    --condition=None

# Permission to "act as" the Scheduler (Vital to avoid deployment failures)
gcloud iam service-accounts add-iam-policy-binding lifeos-scheduler-sa@${PROJECT_ID}.iam.gserviceaccount.com \
    --member="serviceAccount:${CLOUDBUILD_SA}" \
    --role="roles/iam.serviceAccountUser" \
    --project=$PROJECT_ID
```

### 4. Notes on the CI/CD pipeline (cloudbuild.yaml)

The deployment step in Cloud Build requires an environment capable of parsing YAML (yq) and accessing secrets:

*   `curl` is used to download the `yq` binary on the fly since the `gcloud` base image does not include it (and lacks `wget`).
*   The Cloud Build account needs the `roles/secretmanager.secretAccessor` role to be able to extract tokens (e.g., `SYSTEM_CRON_TOKEN`) and inject them into the execution environment of the `deploy_schedulers.sh` script.
